# AI夕飯プラン：テスト環境の準備と確認

更新：テスト用キーの登録と `gemini-3.5-flash-lite` へのJSON通信成功の報告を受けました。まずDBを変更せず実生成を試す手順は [AI-DINNER-NEXT-TEST.md](AI-DINNER-NEXT-TEST.md) を参照してください。以下は登録済み食材を使う通常機能の接続手順です。

このブランチは、先に確認した献立提案ブランチを引き継いでいます。mainへのマージ・本番公開は行っていません。
新しいAI献立は `index.html` の `const dinnerEnabled=false;` により無効です。従来のログイン・共有・写真認識・冷蔵庫・定番料理の提案は維持しています。

## 1. 本番と別のSupabaseプロジェクトを用意する

1. Supabaseでテスト専用プロジェクトを作成します。プロジェクト名とURLを本番と区別してください。
2. 既存アプリと同じデータベース構造・認証・共有用のRLS（行単位アクセス制御）・RPCを、既存の管理元からテスト環境に再現します。現在リポジトリに既存スキーマや `recognize-ingredients` のソースはないため、このブランチだけでは既存バックエンド全体を再構築できません。テーブル名だけから推測したSQLは本番にもテストにも適用しないでください。
3. 本番ユーザー・食材・招待コードはコピーせず、テスト用アカウント2つと架空の冷蔵庫・食材を用意します。
4. `households` と `ingredients` のRLSが有効で、本人・共有相手以外の行が読めないことを確認します。この関数は利用者のJWTをそのまま渡し、RLSを使います。service_roleキーは使いません。
5. 写真認識をテスト環境でも使う場合は、既存の管理元から `recognize-ingredients` をテスト環境に別途配置します。新しい献立関数は既存の写真認識を変更しません。

## 2. Geminiキーをテスト環境のサーバーに保存する

Google AI Studioの管理画面でテスト用キーを準備し、Supabaseの**テスト用プロジェクト**のEdge Functions → Secretsに以下を設定します。キーはチャット、HTML、GitHub、スクリーンショットに貼らないでください。

| 名前 | 設定する内容 |
| --- | --- |
| `GEMINI_API_KEY` | テスト用Geminiキー |
| `GEMINI_MODEL` | `gemini-3.5-flash-lite`（省略時も同じ）。他の構造化JSON対応モデルにも変更可能 |
| `DINNER_ALLOWED_ORIGINS` | 例：`http://localhost:8000`。複数ならカンマ区切り |

`SUPABASE_URL` と `SUPABASE_ANON_KEY` はホストされた関数にSupabaseが提供する値です。既存の同名シークレットを本番で変更する必要はありません。

ローカルHTMLを `file:///.../index.html` で直接開いてテストする場合はOriginが `null` になります。テスト環境の許可元に `null` を明示追加する方法もありますが、他のローカル文書も同じOriginになるため、通常は `http://localhost:8000` の利用を推奨します。どちらの場合も利用者の有効なJWTと共有権限が必要です。`*` は使いません。

Google側で利用枠・課金の上限や通知を設定してください。コード内の1分クールダウンはサーバーの実行単位での補助的な制限であり、分散環境での厳密な課金上限ではありません。厳密な利用回数の制限が必要な場合は共有ストアでのレート制限が別途必要です。

## 3. テスト用の関数だけを配置する

Supabase CLIを利用できる環境で、対象プロジェクトIDが**テスト用**であることを確認してから次を実行します。

```sh
supabase functions deploy generate-dinner --project-ref YOUR_TEST_PROJECT_REF --no-verify-jwt
```

`--no-verify-jwt` は、ゲートウェイの旧JWT検証に依存せず、関数内で `/auth/v1/user` に問い合わせて利用者JWTを検証する構成のためです。未認証のリクエストは関数内で401になります。公開キー・service_roleキーだけで生成はできません。

このコマンドは既存の写真認識やDB構造を更新しません。既存関数をまとめて配置するコマンドは使わないでください。`supabase db push` 等のDB変更もこの機能には不要です。

## 4. テスト用の画面を接続する

1. ブランチのファイルを別のテスト用フォルダーにコピーします。
2. コピーした `index.html` の `const url` と `const key` をテスト用SupabaseのURLと公開キーに置き換えます。ここにGeminiキーやservice_roleキーは絶対に入れません。
3. そのコピーで `const dinnerEnabled=true;` にします。本番URLのまま有効化しないでください。
4. テスト用フォルダーをローカルWebサーバーで開きます（例：Pythonが利用できる場合は `python -m http.server 8000 --bind 127.0.0.1`）。`http://localhost:8000` にアクセスします。
5. テスト専用アカウントでログインします。本番のアカウント・登録データを使わないでください。

`generate-dinner` が未配置の場合、AI献立は接続エラーになります。写真認識は従来通り別の関数です。キーをHTMLに入れて回避しないでください。

## 5. 実際の生成で確認すること

- 卵・鶏肉・玉ねぎ・にんじん・しめじ等を架空の食材として登録し、ボタンを押して毎回3パターン表示されること。
- 各パターンに主菜・副菜・汁物が1品ずつあり、在庫を優先していること。再生成時のvariationは毎回変えますが、似た料理の再出現まで禁止はしていません。
- 各料理に家族3人分の材料・単位付き分量、大人1人／子ども1人の盛り付け目安、下ごしらえ、火加減、時間、加熱の確認、手順があること。
- 取り分けは十分な加熱後・大人用の味付け前であり、大人用の仕上げ量も示されること。野菜の混ぜ込み、キノコの刻み方、薄味・辛味・骨への配慮が妥当なこと。
- 買い足す食材と調味料の確認がプランごとに表示されること。同じ食材でも料理ごとの分量を表示します（単位の自動合算はしません）。在庫は食材名のみの照合なので、数量の不足は利用者が確認します。表記の違いにより買い足し側になる場合があります。
- 食材0件では生成ボタンが無効、生成中の連打ができず、1分以内の再生成はサーバーで制限されること。
- 生成中の冷蔵庫切り替え・食材追加削除・ログアウトで古い献立が表示されないこと。
- 他人の冷蔵庫IDでは403となること。共有された冷蔵庫は2人のテストアカウントで利用できること。
- 回線切断、Geminiの利用上限、不完全な応答でエラーと再試行が表示され、途中までの献立やサーバー秘密情報が出ないこと。
- 開発者ツールの通信にGeminiキーがなく、ブラウザはSupabase関数だけを呼ぶこと。食材の新規登録・削除は従来の操作以外では発生しないこと。
- 既存のログイン、手入力、削除、一括登録、招待・参加、冷蔵庫切り替えをテスト用データで確認すること。

AIが作った調理手順の意味や栄養・食べやすさはJSON形式の検証だけでは保証できません。実生成結果の内容確認も必要です。加熱時間は目安であり、厚さ・器具に応じて中心までの加熱を確認してください。
