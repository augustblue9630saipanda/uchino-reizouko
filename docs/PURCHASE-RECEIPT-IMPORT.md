# 買い物・レシートから冷蔵庫へ（2026-11-25）

## 使い方

### 購入済みの買い物から登録

1. 買い物を購入済みにし、「冷蔵庫へ登録」を開く。
2. 食材だけが初期選択される。日用品・不明な商品は未選択。誤判定はチェックと名前の修正で調整できる。
3. 商品名と購入量の参考を見ながら、食材名を確認。「カテゴリ・残量・登録日」の行を開けば修正できる。残量は並、登録日は日本時間の当日が初期値。
4. 同じ食材があるときは、残量更新・別項目追加・今回は登録しない、から選ぶ。残量更新は更新先を確認し、元の名前・カテゴリ・登録日を維持する。別項目追加は確認画面の日付を使う。
5. 「確認した内容をまとめて反映」。登録済みの買い物は表示に印が付き、次の候補には出ない。使い切って冷蔵庫から削除しても、同じ買い物が勝手に再登録されることはない。同じ商品を再購入する際は新しい買い物項目を追加する。

### レシートから登録

1. 冷蔵庫・買い物の「レシートから登録」を開く。
2. カメラで撮影、または写真・ファイルを選択。会員番号・決済情報などは写さず商品明細だけを選ぶ。長いレシートは分けて撮影する。
3. Google Geminiへ画像を送ることを確認し、「AIで商品を読み取る」を押す。
4. 元の商品名と食材名・分類・購入量を確認し、登録対象を選択。誤読は直し、抜けた食材は手動追加できる。
5. 買い物リストの照合先は候補を確認して自分で選択する。完全一致でも自動確定しない。日用品は食材登録をチェックせず、照合先の「購入済みにする」だけを選べる。
6. 確認後にまとめて反映。画像・元の商品名はDBに保存しない。選んだ食材名や購入状態と、二重処理防止用のキー・件数だけを保存する。

## 共有・二重登録防止

- `commit_pantry_import` はログイン・世帯所属を確認し、食材・買い物・処理済み記録を一つのトランザクションで更新する。
- 手入力の食材追加と同じ世帯ロックを使う。最新の在庫に未確認の重複が見つかれば、何も保存せず確認画面に戻す。
- 登録用バッチIDで通信後の再試行を識別。同じ買い物項目を夫婦が同時に登録しても登録済み状態で防ぐ。日用品の購入済み更新だけでは冷蔵庫登録済みにしない。
- 同じ画像ファイルはSHA-256で識別して再追加しない。別の写真として撮り直した同一レシートは自動判別できないため、買い物との照合・在庫重複確認で判断する。
- 一部だけ選んで確定した同じ画像を再処理しても、新しい登録にはならない。後から必要になった未登録分は手入力する。
- 登録済み管理列は通常のクライアント編集権限から外し、サーバー処理で管理する。既存の世帯RLSを維持。画像はStorage等へアップロードしない。

## 読み取りとエラー処理

- 入力は20MB以下の画像。クライアントで長辺2400px以内のJPEGへ変換し、必要なら圧縮率を調整。送信画像はbase64で約4.8MBまで。
- サーバーは既存のGeminiシークレットを利用。モデル初期値は `gemini-3.5-flash-lite`、必要時のみ `RECEIPT_GEMINI_MODEL` で変更できる。秘密キーはフロントへ渡さない。
- サーバーの通信枠50秒、ブラウザ側65秒。最大60商品・出力8192トークン。自動再試行はしない。失敗時は画像を保持して手動で再試行でき、明細を分けて撮る案内を表示する。
- 文字が不明瞭な商品は不明として未選択。値引き・税額・合計・ポイント・会員番号等は出力対象外で、サーバーでも除外する。画像・OCR生レスポンス・認証情報はログに追加しない。
- アプリ側で画像を保存しない。外部AI側の取扱いはGoogleの利用条件に従うため、個人情報を写さない。

## 配置

1. `202611250001_purchase_pantry_import.sql`、`202611250002_import_flag_permissions.sql` の順に適用。
2. `node scripts/build-receipt-server.mjs` で単一ファイルを生成し、`supabase/dashboard/scan-receipt.ts` を本番 `scan-receipt` へ配置。既存の写真認識・献立関数は変更しない。
3. mainの画面・共通モジュールをGitHub Pagesへ反映。

## 検証結果と未確認事項

- 自動テスト70件成功。OCR契約・商品名変換・メタ情報除外・照合候補・日用品の初期除外・確認前の保存禁止・購入済みだけの更新・重複選択・再試行・世帯切替・タイムアウト解除・既存機能を検証。
- 本番DBのロールバック付きテスト成功。一括追加・残量/日付・古い日付維持・明示的な重複追加・買い物とレシートをまたぐ二重登録防止・写真キー・夫婦の権限・世帯外拒否・原子性を確認。
- 公開アプリで確認用の牛乳/人参/洗剤を使い、食材2件の登録、洗剤の除外、残量/登録日、登録済み表示、再度の候補からの除外を確認。確認用の食材・買い物項目は削除済み。既存データは削除・統合していない。
- レシート画像選択のブラウザ自動操作が停止したため、専用の読み取り専用画面 `tests/receipt-live.html` で架空画像を実送信。登録は行わない。食材4件・日用品1件・不明1件を想定どおり抽出し、税/合計/ポイント/架空会員番号は商品に含まれなかった。
- サンプル1回の実測：ブラウザ全体3390ms、関数2475ms、入力1433トークン・出力356トークン。一般のレシートの精度・所要時間を保証する測定ではない。
- 公式標準有料料金（入力$0.30、出力$2.50 / 100万トークン）でサンプルを換算すると約$0.00132/回。無料枠内なら無料。実際の請求はプロジェクトの契約・上限・画像・明細数・再試行回数による。新規有料サービスは導入していない。[Google公式料金](https://ai.google.dev/gemini-api/docs/pricing/)
- 実際のレシート写真、iPhone実機の撮影/ライブラリ選択、WindowsにインストールしたPWAでのファイル選択、夫婦2端末の同時操作は未確認。読み取りから共通確認への接続は自動テスト、登録処理は本番DBテストで確認しており、実ファイル選択を含めた通し操作は未確認。
